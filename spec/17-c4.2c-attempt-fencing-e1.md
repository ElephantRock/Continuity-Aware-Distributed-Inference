# C4.2c — E1 distributed CPU Attempt-fencing retry races

Status: **validated candidate under issue #53**

Exact base:

`2b8e1466f3995fc5649c65b757ddece080c4516a`

This slice is the final S1 evidence tier under C4.2. It does not change C1, C2, C3, their semantic contracts, or baseline information privileges.

## 1. Research question

C4.2c tests the E1 part of RQ1/H1:

> Under real concurrent CPU execution and real inter-process result delivery, do stale, duplicated, superseded, or delayed Attempt results ever become authoritative for the current LogicalRequest?

The required B4 condition is zero semantic violations under the covered E1 retry races. Comparator separation is a separate question. If competent B0–B3 remain correct because all baselines share the closed C1 semantic commit guard, C4.2c records that null comparator rather than weakening a baseline or counting B4 placement fencing as authoritative correctness.

## 2. Validation stratum

Every C4.2c result uses:

```text
validation_level     EV1_MEASURED_CPU_DISTRIBUTED
evidence_provenance MEASURED
```

The mandatory environment is CPU-only and uses:

```text
coordinator process
one spawned worker process per Attempt
multiprocessing.Pipe command channels
multiprocessing.Queue result/presentation channel
real SHA-256 CPU work in each worker
real OS process scheduling and IPC delivery
real monotonic coordinator retry deadlines
```

The process start method is fixed to `spawn` so workers do not inherit a live C1 semantic store. C1 exists only in the coordinator. Worker processes can execute and report physical results; they cannot mutate semantic authority.

The retry timeout is a fixed experiment input of 5 ms. The coordinator measures it with `time.monotonic()` and loops/sleeps until the deadline has actually elapsed, so an early wakeup cannot shorten the timeout. The fixed duration belongs to policy-independent ground truth; measured timeout start/fire wall timestamps and monotonic elapsed duration belong to observed evidence.

## 3. Semantic boundary

C4.2a/C4.2b established the mandatory distinction:

```text
physical execution != placement admission != authoritative result acceptance
```

C4.2c preserves it exactly.

### Physical execution

A worker process executes bounded SHA-256 work and sends a physical completion over IPC. The coordinator then records the Attempt execution result through the public C1 API.

### Placement admission

If a physical completion belongs to an already-`SUPERSEDED` Attempt, the selected C3 policy receives the same stale-work placement probe used by the earlier S1 slices. A B4 `ATTEMPT_FENCED` decision is recorded as a diagnostic only.

### Authoritative acceptance

A terminal presentation carries request/Attempt/Evidence/Output identity and the worker's original physical-success observation time. The coordinator creates or idempotently reuses terminal Evidence/Output and calls the public C1 `finalize_request` operation. SAAR classification uses the Attempt authority captured immediately before that finalization attempt and the authoritative request state afterward.

## 4. Independent oracle and paired inputs

The scenario specification is fixed before any policy is selected. It contains only policy-independent experimental facts:

- LogicalRequest identity;
- ordered Attempt generations;
- expected current/committed Attempt;
- fixed terminal presentation EventIDs;
- which presentation EventIDs are oracle-stale;
- duplicate-delivery relationships;
- concurrency/presentation groups;
- fixed CPU-work configuration and process topology;
- fixed retry-timeout duration used by the real monotonic coordinator deadline.

Measured worker PIDs, process timestamps, timeout elapsed durations, physical completion order, and concurrent IPC delivery order are **observed evidence**, not ground truth. Consequently B0–B4 records for a scenario have identical `ground_truth_json` and identical exogenous SAAR opportunity signatures even when OS scheduling produces different measured delivery orders.

## 5. Mandatory E1 scenario corpus

The implementation fixes six scenarios.

### E1-A — stale before fresh

A real monotonic coordinator timeout expires while A1 remains unfinished; A2 then starts and supersedes it. A1 and A2 then execute in separate worker processes. The stale A1 terminal presentation is delivered before the current A2 presentation.

Expected authority: A2.

SAAR opportunities: 1.

### E1-B — fresh before stale

Same retry race, but the current A2 terminal presentation commits first and the stale A1 presentation arrives afterward.

Expected authority: A2.

SAAR opportunities: 1.

### E1-C — duplicate result delivery

After retry, A2 is presented and then delivered again as a true duplicate. A1 is subsequently presented twice as a true stale duplicate pair.

For each duplicate pair:

```text
AttemptID        identical
EvidenceID       identical
OutputID         identical
observed_at      identical
delivery EventID distinct
```

The fresh duplicate must be idempotent rather than a second semantic finalization. Both stale deliveries remain separate SAAR denominator events.

Expected authority: A2.

SAAR opportunities: 2.

### E1-D — success before timeout, observation after supersession

A1 physically succeeds and C1 records `SUCCEEDED` while A1 is still `CURRENT`. Its terminal observation is withheld. A real monotonic coordinator timeout then starts only after that physical completion has been delivered to the coordinator and then expires; A2 starts, superseding the already-successful A1, and the delayed A1 terminal presentation arrives afterward.

This case distinguishes physical success time from authority at terminal presentation.

Expected authority: A2.

SAAR opportunities: 1.

### E1-E — concurrent terminal race

A1 is stale and A2 is current. Their terminal presentation commands are issued as one concurrency group to distinct worker processes. The coordinator consumes the two real IPC deliveries in whichever order the OS produces.

The oracle does not depend on arrival order: A1 remains stale and A2 remains the only correct authoritative Attempt.

Expected authority: A2.

SAAR opportunities: 1.

### E1-F — three-generation retry race

A1 starts, a measured timeout expires, A2 supersedes A1, a second measured timeout expires, and A3 supersedes A2 before the unfinished workers are released for CPU completion. A1, A2, and A3 execute in distinct processes and their terminal presentations are released as one concurrency group.

Expected authority: A3.

SAAR opportunities: 2.

## 6. Fixed denominators

Across the six scenarios, each policy receives:

```text
SAAR exogenous opportunities  8
DFR policy-derived requests   6, when all six LogicalRequests complete
SSER faulted operations       6
```

SAAR denominator EventIDs are fixed by the scenario specifications before policy execution. Physical completion EventIDs and retry-timeout observations are not SAAR opportunities.

DFR counts semantic finalization, not message cardinality. A duplicate delivery that reuses the already-authoritative Output and leaves C1 unchanged is idempotent and is not a DFR violation.

## 7. Anti-false-zero requirements

The E1 harness must not turn a real stale acceptance into an exception that suppresses the metric.

For each oracle-stale terminal presentation:

1. capture Attempt execution/authority and committed-request identity before finalization;
2. attempt the real C1 terminal finalization;
3. capture authority and committed-request identity afterward;
4. classify acceptance from the pre/post snapshots.

If an earlier defective stale presentation has already changed the stale Attempt from `SUPERSEDED` to `COMMITTED`, a later duplicate stale presentation remains an oracle-stale input and must stay measurable. The classifier therefore accepts the prior-bad-commit state only as causal fallout from an earlier stale acceptance; it does not reinterpret the Attempt as fresh.

Every declared SAAR EventID must appear in the recorded finalization attempts. Missing IPC delivery or a worker/process failure must fail the experiment instead of silently shrinking the denominator.

Every retry must also have exactly one corresponding measured timeout observation, and measured monotonic elapsed duration must be at least the fixed timeout duration.

## 8. C3 fairness

All five policies receive the closed C3 information contract. The E1 semantic store is common C1 authority for B0–B4.

B4 may reject stale physical-work placement with:

`ATTEMPT_FENCED`

That result remains outside SAAR. B0–B3 retain their ordinary placement behavior and the common C1 semantic finalization guard. No baseline is stripped of the shared semantic guard to manufacture an H1 effect.

## 9. Required record shape

Every E1 trial produces the existing `cadi.correctness-evaluation.v1` record with the four required fields separated:

```text
ground_truth
observed_evidence
policy_decision
semantic_result
```

`ground_truth` contains only the fixed E1 scenario/oracle specification, including the fixed retry-timeout duration.

`observed_evidence` contains measured process PIDs, worker lifecycle observations, monotonic retry-timeout elapsed durations, timeout start/fire wall timestamps, compute-ready batches, physical completion records, terminal-presentation preconditions, actual IPC delivery order, terminal finalization outcomes, and the resulting authoritative C1 state.

`policy_decision` contains the common semantic-authority declaration and the separate stale-work placement diagnostics.

`semantic_result` uses the existing O1–O4 contract. Successful retry recovery is O2. A semantically incorrect authoritative success is O4. Explicit non-success remains O3 and is not silently converted into a correctness failure.

## 11. Exit gate

C4.2c may merge only when all of the following hold on one exact reviewed head:

- all six real-process scenarios execute for B0–B4;
- every trial is EV1 / MEASURED;
- every retry is preceded by its measured monotonic timeout trigger;
- all exogenous paired ground truth and SAAR EventIDs are policy-invariant;
- every declared stale presentation reaches real C1 finalization;
- duplicate delivery preserves semantic identity and original `observed_at`;
- DFR measures applied semantic finalization rather than repeated transport delivery;
- worker/process failures cannot silently shrink denominators;
- supported Python 3.11 / 3.12 / 3.13 CI is green;
- bounded exact-head review has no unresolved substantive correctness or measurement-integrity finding.

After merge, C4.2 closes only after #48 explicitly adjudicates H1 from C4.2a + C4.2b + C4.2c. Given the current E0 + E1 evidence, if no review finding changes the result, H1 must be narrowed: Attempt authority remains a valid semantic mechanism, but the experiments do not demonstrate an independent B4 correctness advantage over competent weaker baselines that share the common C1 semantic commit guard.
