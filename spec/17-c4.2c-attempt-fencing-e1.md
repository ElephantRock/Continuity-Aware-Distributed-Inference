Status: **final review candidate under issue #53**

`2b8e1466f3995fc5649c65b757ddece080c4516a`

## 1. Research question

C4.2c tests the E1 part of RQ1/H1:

> Under real concurrent CPU execution and real inter-process result delivery, do stale, duplicated, superseded, or delayed Attempt results ever become authoritative for the current LogicalRequest?

The required B4 condition is zero semantic violations under the covered E1 retry races. Comparator separation is a separate question. If competent B0–B3 remain correct because all baselines share the closed C1 semantic commit guard, C4.2c records that null comparator rather than weakening a baseline or counting B4 placement fencing as authoritative correctness.

## 2. Validation stratum

Every C4.2c result uses:

```text
validation_level     EV1_MEASURED_CPU_DISTRIBUTED
evidence_provenance MEASURED
```

The mandatory environment is CPU-only and uses:

```text
coordinator process
one spawned worker process per Attempt
multiprocessing.Pipe command channels
multiprocessing.Queue result/presentation channel
real SHA-256 CPU work in each worker
real OS process scheduling and IPC delivery
real monotonic coordinator retry deadlines
```

The process start method is fixed to `spawn` so workers do not inherit a live C1 semantic store. C1 exists only in the coordinator. Worker processes can execute and report physical results; they cannot mutate semantic authority.

The retry timeout is a fixed experiment input of 5 ms. The coordinator measures it with `time.monotonic()` and loops/sleeps until the deadline has actually elapsed, so an early wakeup cannot shorten the timeout. The fixed duration belongs to policy-independent ground truth; measured timeout start/fire wall timestamps and monotonic elapsed duration belong to observed evidence.

For `RETRY_RACE` scenarios, each superseded Attempt has a fixed minimum 20 ms **process-CPU** work floor measured in the worker with `time.process_time()`. A worker emits a `COMPUTE_STARTED` IPC observation immediately before beginning SHA-256 work, and the coordinator does not start that Attempt's retry timeout until `COMPUTE_STARTED` has been received. The required measured wall-clock ordering is:

```text
CPU started <= timeout start <= timeout fire <= physical completion
```

The 20 ms process-CPU floor and 5 ms timeout are fixed experiment inputs. Actual process scheduling, wall-clock timestamps, monotonic timeout elapsed duration, process CPU consumed, and completion order remain observed evidence and are never exposed to the policy as oracle ground truth. The process-CPU floor does not assume or require 20 ms of wall-clock residency; descheduling may make wall elapsed time larger.

## 3. Semantic boundary

C4.2a/C4.2b established the mandatory distinction:

```text
physical execution != placement admission != authoritative result acceptance
```

C4.2c preserves it exactly.

### Physical execution

A worker process executes bounded SHA-256 work and sends a physical completion over IPC. The coordinator then records the Attempt execution result through the public C1 API.

### Placement admission

If a physical completion belongs to an already-`SUPERSEDED` Attempt, the selected C3 policy receives the same stale-work placement probe used by the earlier S1 slices. A B4 `ATTEMPT_FENCED` decision is recorded as a diagnostic only.

### Authoritative acceptance

A terminal presentation carries request/Attempt/Evidence/Output identity and the worker's original physical-success observation time. The coordinator creates or idempotently reuses terminal Evidence/Output and calls the public C1 `finalize_request` operation. SAAR classification uses all relevant authoritative channels after finalization: committed AttemptID, stale Attempt authority, and authoritative OutputID.

## 4. Independent oracle and paired inputs

The scenario specification is fixed before any policy is selected. It contains only policy-independent experimental facts:

- LogicalRequest identity;
- ordered Attempt generations;
- expected current/committed Attempt;
- fixed terminal presentation EventIDs;
- which presentation EventIDs are oracle-stale;
- duplicate-delivery relationships;
- concurrency/presentation groups;
- fixed CPU-work configuration and process topology;
- fixed minimum process-CPU seconds for retry-race Attempts;
- fixed retry-timeout duration used by the real monotonic coordinator deadline.

Measured worker PIDs, process timestamps, process CPU consumed, timeout elapsed durations, physical completion order, and concurrent IPC delivery order are **observed evidence**, not ground truth. Consequently B0–B4 records for a scenario have identical `ground_truth_json` and identical exogenous SAAR opportunity signatures even when OS scheduling produces different measured delivery orders.

## 5. Mandatory E1 scenario corpus

The implementation fixes six scenarios.

### E1-A — stale before fresh

A1 begins real CPU work in its own process. After the coordinator observes `COMPUTE_STARTED`, a real 5 ms monotonic retry timeout begins and expires while A1 remains physically in flight. A2 then starts and semantically supersedes A1. A1's physical completion occurs after the timeout and is recorded as stale. The stale A1 terminal presentation is delivered before the current A2 presentation.

Expected authority: A2.

SAAR opportunities: 1.

### E1-B — fresh before stale

A1 again begins real CPU work before its retry timeout and physically completes only after that timeout has fired and A2 has superseded it. The current A2 terminal presentation commits first and the stale A1 presentation arrives afterward.

Expected authority: A2.

SAAR opportunities: 1.

### E1-C — duplicate result delivery

A1 begins real CPU work before the measured retry timeout; A2 supersedes A1 after the timeout fires. A2 is presented and then delivered again as a true duplicate. A1 is subsequently presented twice as a true stale duplicate pair.

For each duplicate pair:

```text
AttemptID        identical
EvidenceID       identical
OutputID         identical
observed_at      identical
delivery EventID distinct
```

The fresh duplicate must be idempotent rather than a second semantic finalization. Both stale deliveries remain separate SAAR denominator events.

Expected authority: A2.

SAAR opportunities: 2.

### E1-D — success before timeout, observation after supersession

E1-D is the deliberate inverse control for the retry-race ordering. A1 physically succeeds and C1 records `SUCCEEDED` while A1 is still `CURRENT`. Its terminal observation is withheld. A real monotonic coordinator timeout starts only after that physical completion has been delivered to the coordinator and then expires; A2 starts, superseding the already-successful A1, and the delayed A1 terminal presentation arrives afterward.

Its required ordering is therefore:

```text
A1 physical completion while CURRENT <= timeout start <= timeout fire <= A2 supersession <= delayed A1 terminal presentation
```

This case distinguishes physical success time from authority at terminal presentation.

Expected authority: A2.

SAAR opportunities: 1.

### E1-E — concurrent terminal race

A1 begins real CPU work before its measured retry timeout and physically completes only after that timeout has fired. A2 is current. Their terminal presentation commands are issued as one concurrency group to distinct worker processes, and the coordinator consumes the two real IPC deliveries in whichever order the OS produces.

The oracle does not depend on arrival order: A1 remains stale and A2 remains the only correct authoritative Attempt.

Expected authority: A2.

SAAR opportunities: 1.

### E1-F — three-generation retry race

A1 begins CPU work, then its measured timeout fires while A1 is still in flight. A2 starts and supersedes A1. A2 then begins CPU work, and a second measured timeout fires while A2 is still in flight. A3 starts and supersedes A2. Both superseded A1 and A2 physical completions occur after their corresponding timeout fires. A3 remains current and is the only correct authoritative Attempt. A1, A2, and A3 terminal presentations are released as one concurrency group.

Expected authority: A3.

SAAR opportunities: 2.

## 6. Fixed denominators

Across the six scenarios, each policy receives:

```text
SAAR exogenous opportunities  8
DFR policy-derived requests   6, when all six LogicalRequests complete
SSER faulted operations       6
```

SAAR denominator EventIDs are fixed by the scenario specifications before policy execution. Physical completion EventIDs and retry-timeout observations are not SAAR opportunities.

DFR counts semantic finalization, not message cardinality. A duplicate delivery that reuses the already-authoritative Output and leaves C1 unchanged is idempotent and is not a DFR violation. Conversely, any completed-to-completed mutation of authoritative request/Attempt state is an applied semantic finalization and must be counted.

## 7. Anti-false-zero requirements

The E1 harness must not turn a real stale acceptance or duplicate finalization into an exception or idempotence label that suppresses the metric.

For every terminal presentation, the harness takes a complete authoritative snapshot immediately before and after the real C1 `finalize_request` call. The snapshot includes:

- request status;
- current AttemptID;
- committed AttemptID;
- authoritative OutputID;
- every request Attempt's authority and execution state.

Finalization outcome is classified from those complete snapshots:

```text
authoritative state changed     -> APPLIED
authoritative state unchanged + ContinuityError -> REJECTED
authoritative state unchanged + success          -> IDEMPOTENT
```

For every oracle-stale terminal presentation:

1. capture Attempt execution/authority and request authority before finalization;
2. attempt the real C1 terminal finalization;
3. capture the complete authoritative state afterward;
4. classify stale acceptance from committed AttemptID, stale Attempt authority, and authoritative OutputID;
5. only after the metric-relevant classification, run the structural invariant oracle.

If the post-finalization state is structurally invalid, the invariant failure is recorded as measured diagnostic evidence (`invariant_error_type` / `invariant_error_message`). Structural corruption can surface through assertion-style violations or through ordinary lookup/type exceptions such as a `KeyError` caused by a dangling authoritative reference. The post-finalization oracle therefore records ordinary `Exception` failures as diagnostics after metric classification rather than allowing them to erase the presentation event. It does **not** catch `BaseException` classes such as process termination or keyboard interruption.

This diagnostic catch is not allowed to hide a defect in the actual E1 corpus. Every real non-injected terminal presentation is regression-checked to require `invariant_error_type is None` and `invariant_error_message is None`.

If an earlier defective stale presentation has already made the stale Attempt or stale Output authoritative, a later duplicate stale presentation remains an oracle-stale input and must stay measurable. The classifier accepts such prior-bad-authority states only as causal fallout from earlier corruption; it does not reinterpret the Attempt as fresh.

Every declared SAAR EventID must appear in the recorded finalization attempts. Missing IPC delivery or a worker/process failure must fail the experiment instead of silently shrinking the denominator.

Every retry must also have exactly one corresponding measured timeout observation. For every `RETRY_RACE` supersession, the worker's `COMPUTE_STARTED` observation must precede the timeout start, measured timeout elapsed duration must be at least 5 ms, physical completion must occur no earlier than timeout fire, and measured worker `compute_cpu_seconds` must be at least 20 ms.

## 8. Measurement-integrity findings and repairs

The final candidate incorporates six substantive hardenings found after the first green E1 implementation.

### Finding 1 — stale acceptance could be suppressed by invariant failure

Codex P1 on exact reviewed head `3591a23a0309250110cb17bed835093f5904aa76` found that a defective stale finalization could commit stale A1 but leave A2 `CURRENT`, causing the structural invariant check to raise before SAAR classification.

Repair: classify and record stale acceptance from the complete pre/post authoritative state before running invariant diagnostics. Regression `test_bad_stale_commit_is_classified_before_invariant_failure` injects exactly this defective finalization and proves the stale acceptance remains measurable while the invariant error is separately recorded.

### Finding 2 — completed-to-completed mutation could be mislabeled idempotent

Codex P1 on the same reviewed head found that a second semantic finalization could mutate authoritative state while request status stayed `COMPLETED`, yet the old classifier could label it `IDEMPOTENT` and leave DFR at zero.

Repair: classify applied finalization from complete authoritative-state mutation, not request status alone. Regression `test_completed_to_completed_semantic_mutation_counts_as_second_applied_finalization` injects a second authoritative-output mutation and proves both semantic finalizations are counted as `APPLIED`.

### Finding 3 — earlier E1 retry races did not prove CPU work was physically in flight

The earlier candidate used real worker processes but most stale CPU work was released only after semantic supersession. That was sufficient for stale-result handling but weaker than the intended E1 retry-race claim.

Repair: workers emit `COMPUTE_STARTED`; the coordinator starts each `RETRY_RACE` timeout only after receiving that observation, and a fixed work floor plus measured ordering ensures the 5 ms timeout fires before physical completion. Regressions require the measured ordering for every superseded retry-race Attempt, including both A1 and A2 in E1-F.

During this hardening, one regression initially required A2 CPU execution to begin before A1 physically completed. Hosted-runner process-spawn latency showed that requirement was stronger than the research contract: A1 can validly remain in flight through its timeout, then complete before A2's separate process reaches CPU execution. That unsupported assertion was removed; the actual retry-race ordering checks were not weakened.

### Finding 4 — stale acceptance classifier ignored partial authority corruption

Codex P1 on exact reviewed head `d368ab265aa08f281376101c0317b3a53d2568f6` found that a defective finalization could make the stale Output authoritative or mark the stale Attempt `COMMITTED` while leaving `committed_attempt_id` pointing at the current Attempt. The old classifier could therefore report false-zero SAAR despite stale authority entering the semantic state.

Repair: stale acceptance is now positive if **any** relevant authoritative channel reflects the stale presentation: committed AttemptID equals the stale Attempt, the stale Attempt authority is `COMMITTED`, or the request authoritative OutputID equals the presented stale Output. The stale precondition also tolerates those prior-corruption states only so later oracle-stale duplicate deliveries remain measurable. Parameterized regression `test_stale_acceptance_detects_partial_authority_corruption` injects stale-output-only and stale-Attempt-authority-only corruption and requires `accepted_authoritatively=True` plus an invariant diagnostic.

### Finding 5 — wall-clock floor did not prove process CPU consumption

Codex P1 on the same reviewed head found that a 20 ms `time.monotonic()` floor could be satisfied mostly by worker descheduling on an oversubscribed runner. That could overstate how much CPU work was actually in flight.

Repair: the worker now measures the 20 ms floor with per-process `time.process_time()`. Wall/monotonic timestamps remain separate and are used only for timeout and delivery ordering. Physical completion records include `compute_cpu_seconds`; regressions require at least 20 ms of process CPU for each superseded `RETRY_RACE` Attempt. No cross-clock numerical comparison is made between process CPU time and wall elapsed time.

### Finding 6 — structural-oracle lookup failure could still suppress a measured stale acceptance

Codex P1 on exact reviewed head `6e1967d09f22343a12ed39d989ec166188cf28f7` found that a defective stale finalization could successfully enter stale authority while leaving a dangling authoritative reference. `InvariantOracle.assert_all()` could then raise `KeyError` while resolving that reference. Because the harness caught only `AssertionError` and `SemanticViolation`, the already-classified stale acceptance could still be lost before the presentation record returned.

Repair: post-finalization structural-oracle diagnostics now capture ordinary `Exception` failures after stale-acceptance/finalization classification. `BaseException` is deliberately not swallowed. Regression `test_dangling_authoritative_reference_is_recorded_after_stale_acceptance` constructs a completed stale commit whose only remaining structural defect is a dangling authoritative OutputID, proves `accepted_authoritatively=True`, and requires `invariant_error_type == "KeyError"`. Regression `test_real_e1_presentations_have_no_invariant_diagnostics` simultaneously requires every real, non-injected E1 terminal presentation to remain invariant-clean, preventing the broader diagnostic boundary from hiding a harness defect.

## 9. C3 fairness

All five policies receive the closed C3 information contract. The E1 semantic store is common C1 authority for B0–B4.

B4 may reject stale physical-work placement with:

`ATTEMPT_FENCED`

That result remains outside SAAR. B0–B3 retain their ordinary placement behavior and the common C1 semantic finalization guard. No baseline is stripped of the shared semantic guard to manufacture an H1 effect.

## 10. Required record shape

Every E1 trial produces the existing `cadi.correctness-evaluation.v1` record with the four required fields separated:

```text
ground_truth
observed_evidence
policy_decision
semantic_result
```

`ground_truth` contains only the fixed E1 scenario/oracle specification, including fixed retry-timeout duration and fixed minimum process-CPU seconds.

`observed_evidence` contains measured process PIDs, worker lifecycle and `COMPUTE_STARTED` observations, measured process CPU seconds, monotonic retry-timeout elapsed durations, timeout start/fire wall timestamps, physical completion records, terminal-presentation preconditions, actual IPC delivery order, terminal finalization outcomes, invariant diagnostics, and the resulting authoritative C1 state.

`policy_decision` contains the common semantic-authority declaration and the separate stale-work placement diagnostics.

`semantic_result` uses the existing O1–O4 contract. Successful retry recovery is O2. A semantically incorrect authoritative success is O4. Explicit non-success remains O3 and is not silently converted into a correctness failure.
