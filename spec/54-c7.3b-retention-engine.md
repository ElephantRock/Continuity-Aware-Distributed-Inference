## Shared Program realization

A `RetentionProgramCase` is immutable and binds Program/Session/State identity, State byte size, initial dependent lifecycle, logical event times, event ordinals, independent semantic-validity outcomes, and Program bounds. Every declared State has at least one admission event. The first admission establishes logical State production for the retention slice. Later `ADMIT` events are common, policy-independent re-admission opportunities: a policy for which the State is nonresident performs a re-admission, while a policy already retaining that immutable State records `ALREADY_RESIDENT` and makes no retention-state change.

The State-level `admission_ordinal` validates the deterministic global order of **first** State admissions and is not a free tuning parameter. For the frozen LRU tie-break, each actual admission/re-admission interval receives the deterministic global ordinal of its `ADMIT` occurrence; re-admission therefore obtains a new admission ordinal. Successful reuse refreshes the primary `last_touch_time_seconds` key but does not change the admission occurrence ordinal. An `ADMIT` opportunity against an already-resident State does not refresh recency or fixed-TTL expiry. Reuse or invalidation before the first State admission is invalid.

Session and dependent-lifecycle transitions remain common ground-truth harness inputs. A retention policy cannot change State identity, State size, event order, semantic validity, or reuse-opportunity count.

## Event order

C7.3b executes the exact C7.3a equal-time sequence:

```text
1  validity invalidation and common INVALID release
2  common Continuation/Session transitions and lifecycle recomputation
3  policy-specific lifecycle or Session-end release
4  fixed-TTL expiry
5  reuse lookup and semantic-validity decision
6  successful reuse touch/accounting
7  State admission / re-admission opportunity
8  capacity enforcement
9  residency interval checkpoint
```

Implicit fixed-TTL expiry times are inserted into the deterministic logical-time stream. Expiry at equality is processed before a same-time reuse. An actual re-admission under fixed TTL starts a new admission-anchored expiry; reuse and an already-resident `ADMIT` opportunity never refresh it.

## Policy adapters

Exactly four retention policies are supported:

```text
LRU
FIXED_TTL
SESSION_PINNING
LIFECYCLE_B4
```

LRU and fixed TTL receive common semantic validity but no lifecycle information for retention ranking or release. Session pinning receives Session identity/live status only. Lifecycle B4 receives StateLifecycle. Terminal-but-valid State remains resident under LRU/fixed TTL until ordinary eviction, TTL expiry, invalidation, or Program end.

LRU successful reuse refreshes recency. Fixed TTL remains admission-anchored and reuse does not refresh expiry; ordinary pressure among unexpired State uses the same deterministic LRU key. Session-pinned State and B4 ACTIVE/PROTECT State are not silently evicted to repair infeasibility.

## Capacity

Each retention manifest binds the exact policy-independent reference working set and derived byte capacity from C7.3a. The engine recomputes the reference working set from Program truth before execution and rejects manifest drift.

Admission/re-admission and capacity enforcement form the frozen adjacent phase boundary. When multiple same-time admissions require multiple ordinary evictions, the engine computes all required evictions before exposing the phase-8 audit snapshots; no audit-observable resident set exceeds capacity. The deterministic eviction order is still recorded per State. If required session-pinned bytes or B4 ACTIVE/PROTECT bytes exceed capacity, the result is `CAPACITY_INFEASIBLE`; capacity is not enlarged and protected State is not silently evicted.

## Reuse and correctness

Every `REUSE` event is a policy-independent eligible opportunity. The engine consumes reuse only when both conditions hold:

```text
independent semantic-validity outcome == true
common State validity == VALID
```

A semantic rejection never becomes an efficiency win. Residency cannot override semantic validity. The same Program case therefore defines the same reuse denominator for all four retention policies.

## Residency accounting

Residency intervals start at admission/re-admission or immediately after successful reuse. They close on successful reuse, eviction, TTL expiry, policy release, invalidation, or Program end. An interval ending in successful reuse is useful; every other classified interval is wasted. The result records useful, wasted, total byte-seconds and their exact partition fractions.
