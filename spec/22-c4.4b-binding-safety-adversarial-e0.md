# 1. Research boundary

C4.4b extends the closed C4.4a Binding-safety harness without changing C1, C2, C3, the baseline information contracts, or the C4.1 correctness record.

The canonical Binding safety rule remains:

```text
ownership-sensitive commit(y, e) => e == CurrentEpoch(y)
```

with safe migration requiring sufficient Evidence and one semantic transition of `(CurrentEpoch, ActiveBinding)`.

The experiment preserves the C4.4a stage separation:

```text
physical transfer/materialization observation
!= policy migration admission
!= authoritative C1 migration commit
!= stale/conflicting Binding presentation
!= semantic outcome
```

# 2. Baseline fairness

All B0–B4 retain the closed common C1 `commit_migration(...)` authority.

```text
B0  request/load only
B1  candidate-key cache locality
B2  session affinity + B1
B3  exact StateID + precise State location, Binding-blind
B4  BindingID + Binding epoch + reconciliation in the frozen Continuity view
```

Only B4 exposes the frozen `decide_migration(...)` admission surface. Its `WAIT`/`ALLOW_COMMIT` result is diagnostic evidence; authoritative correctness is determined by C1 state after the actual Binding presentation.

No weaker baseline bypasses the C1 base-epoch/status/evidence guard.

# 3. Pressure families

C4.4b covers five deterministic adversarial families:

```text
A  multi-epoch depth and reordered stale-owner presentation
B  concurrent candidate races and winner ordering
C  migration Evidence scope/sufficiency faults
D  partial materialization / failover before commit
E  repeated/replayed stale Binding presentations
```

Ambiguous Evidence is intentionally not used as an S3 comparator pressure because ambiguous-commit safety is primarily C4.5/S4. C4.4b uses only missing or mis-scoped `EXACT_OBSERVATION` Evidence to exercise D5.

# 5. Multi-epoch and concurrent pressure

## Family A

The first three cases commit two or three sequential migrations, then present a stale epoch-1 or epoch-2 Binding.

Expected authority examples:

```text
epoch 1 -> epoch 2 -> epoch 3
late epoch 1 or epoch 2 -> rejected
CurrentEpoch remains 3
```

and:

```text
epoch 1 -> epoch 2 -> epoch 3 -> epoch 4
late epoch 1 -> rejected
CurrentEpoch remains 4
```

## Family B

Several candidates are allocated from one base epoch before any commits.

The corpus intentionally includes both conventional and reordered winner selection:

```text
b2 epoch2, b3 epoch3, b4 epoch4 all base1
```

with cases where:

```text
b2 wins
b3 wins before b2
b3 wins among b2/b3/b4
```

Only one Binding may become authoritative. Later candidates whose `base_epoch` no longer equals `CurrentEpoch` must be fenced even if they hold otherwise valid commit Evidence.

A higher allocated epoch winning first is not itself invalid: D2 requires monotonicity, not contiguous epoch consumption. The safety requirement is single current authority and stale-base fencing after commit.

---

# 6. Evidence and partial-failover pressure

Family C uses a single next-epoch candidate and varies only commit Evidence:

```text
no Evidence
EXACT_OBSERVATION with wrong Binding scope
EXACT_OBSERVATION with wrong epoch scope
valid EXACT_OBSERVATION control
```

The first three must fail semantic commit and remain explicit WAIT/non-success; the control must commit normally.

Family D models:

```text
destination failure before semantic commit
partial destination materialization followed by a different successful migration
```

Physical destination existence/failure is recorded as deterministic experiment evidence only. It does not mutate Binding authority.

A late partially materialized candidate must be fenced after the alternate Binding commits.

---

# 7. Replay pressure

Family E includes:

```text
duplicate winner commit after the winner is already ACTIVE
repeated stale loser presentation after an earlier rejection
repeated old-owner presentation after three epoch advances
valid sequential next-epoch migration control
```

The closed C1 migration API rejects re-presented committed/stale candidates rather than treating them as a second semantic commit. The correctness requirement is that replay never changes authoritative Binding state.

The corpus distinguishes semantic Binding replay from transport-level duplicate identity. Transport cardinality/duplicate-event identity is reserved for C4.6 where idempotence/ordering is the primary mechanism under test.

# 8. Oracle boundary

Every manifest declares:

```text
expected final BindingID
expected final epoch
fault class
SBDR EventID
presentation BindingID
Evidence mode
reconciliation input
```

These expectations are independent of policy output.

Nominal setup commits are executed and recorded separately from the final adversarial presentation. Setup commits are required to pass C1 invariants; a malformed setup fails the experiment rather than being silently attributed to the final SBDR denominator event.

After the final presentation, the classifier compares actual C1 authority against the manifest pair.

# 9. Metric contract

## SBDR

The 14 faulted cases provide 14 exogenous paired opportunities per policy.

A violation requires actual authoritative divergence from the manifest after the final presentation.

Rejected, WAITed, or failed stale operations are not SBDR violations.

## SSER

The same 14 faulted operations form the SSER denominator.

Expected faulted outcome partition under the common C1 authority:

```text
O1  10
O2   0
O3   4
O4   0
```

The four O3 cases are:

```text
missing commit Evidence
wrong Binding Evidence scope
wrong epoch Evidence scope
destination failure before commit
```

# 10. Anti-false-zero regression

As in C4.4a, a private corruption hook is used only by regression tests after the real C1 presentation path.

Forcing the stale presented Binding to become current must produce:

```text
SBDR > 0
O4
```

This demonstrates that a real Binding divergence remains measurable and is not hidden by a pre-classification assertion or by normal C1 rejection.
