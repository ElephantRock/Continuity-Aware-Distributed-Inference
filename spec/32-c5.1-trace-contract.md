# 32 — C5.1 Normalized Public-Trace Contract

## Status

C5.1 implementation contract under C5 issue #90 / tracker #91.

Base milestone: Gate G1 / C4 closure `893160c791245df422f7caf5dcb77459a7675087`.

## Purpose

C5 introduces EV2 trace-driven workload realism. Before selecting a public dataset, this slice freezes the source-neutral representation used to ingest traces and makes provenance boundaries executable.

C5.1 is **not an EV2 empirical result**. Its tests use synthetic fixtures only to validate serialization, identity, missingness, and provenance rules.

The canonical C5 data strategy remains:

```text
public workload distributions
+
synthetic Continuity structure
+
controlled fault injection
```

Those three components must remain distinguishable in every later workload artifact.

## Schema

Canonical dataset schema:

```text
cadi.c5.1.normalized-trace.v1
```

A dataset contains exactly:

```text
schema
manifest
records
```

Unknown or missing JSON members fail validation rather than being silently ignored.

## Source manifest

`TraceSourceManifest` records:

```text
source_id
source_name
source_uri
source_version
license_id
source_sha256
normalization_version
normalization_steps
field_origins
```

`source_sha256` is a lowercase 64-character SHA-256 digest. C5.2+ adapters must compute it from the exact source artifact bytes used for normalization.

`normalization_steps` is ordered and non-empty. It records mechanical transformations such as timestamp-unit conversion or token-count derivation.

### Field provenance

For source-layer workload fields, C5.1 permits only:

```text
SOURCE_OBSERVED
TRACE_DERIVED
```

There is intentionally no synthetic provenance value in the source-record layer. A later Continuity augmentation layer must be a separate object/schema so that sessions, branches, tool waits, retries, and injected faults cannot be mistaken for public-trace observations.

`arrival_time_s` provenance is mandatory. Any optional field that is present in at least one normalized record must have a manifest provenance declaration.

## Normalized source record

`NormalizedTraceRecord` contains exactly:

```text
record_id
source_record_id
source_ordinal
arrival_time_s
input_tokens
output_tokens
prefix_group_id
prefix_tokens
```

Interpretation:

- `record_id`: stable normalized identity inside the normalized dataset;
- `source_record_id`: stable identity from the source or an adapter-defined deterministic source-row identity;
- `source_ordinal`: original source ordering position, preserved independently of replay time;
- `arrival_time_s`: finite, nonnegative normalized seconds;
- `input_tokens`: nonnegative integer or explicit `null`;
- `output_tokens`: nonnegative integer or explicit `null`;
- `prefix_group_id`: source-observed/trace-derived reuse grouping or explicit `null`;
- `prefix_tokens`: source-observed/trace-derived reusable-prefix length or explicit `null`.

If `prefix_tokens` is present, `input_tokens` must also be present and:

```text
0 <= prefix_tokens <= input_tokens
```

C5.1 does not impute absent fields.

## Identity and ordering invariants

Within one dataset:

```text
record_id          unique
source_record_id   unique
source_ordinal     unique
```

Canonical serialization stores records in ascending `source_ordinal` order. This preserves source order even if a source artifact is initially presented to the constructor in a different container order.

Chronological replay order is a separate projection:

```text
sort by (arrival_time_s, source_ordinal)
```

This prevents the normalization layer from conflating source-row order with event-time order and gives simultaneous arrivals a deterministic tie-breaker.

## Missingness and field requirements

Missing optional source information is represented as JSON `null` and survives round trip.

`field_coverage()` mechanically reports `(present_count, total_count)` for every normalized workload field.

`require_fields(...)` allows a downstream experiment to declare the fields it actually needs. It rejects a dataset when any requested field is missing from any record instead of silently fabricating or imputing values.

Examples:

```text
an arrival-only burstiness experiment
    may require arrival_time_s only

an EV3 prefill/decode workload
    may later require input_tokens + output_tokens

an exact prefix-reuse experiment
    may require prefix_tokens
```

The requirement belongs to the consuming experiment, not to hidden adapter behavior.

## Canonical serialization and fingerprint

Serialization uses deterministic JSON with:

```text
sorted object keys
explicit nulls
no NaN / Infinity
no duplicate JSON members
exact schema members
```

The dataset fingerprint is:

```text
SHA256(canonical UTF-8 JSON of complete manifest + records)
```

Therefore it binds source provenance, normalization description, field provenance, source ordering, timings, lengths, prefix fields, and explicit missingness.

The fingerprint is stable under JSON object-member insertion order but changes when a semantic record or manifest value changes.

## Scientific boundary

C5.1 establishes only the data/provenance contract. It does not establish:

- that any particular public trace is suitable;
- that an external trace is licensed for redistribution;
- that source data contains session/branch/tool semantics;
- that an absent prefix-reuse signal may be imputed and called trace-derived;
- physical GPU latency, throughput, or memory costs;
- H4/H5/H7 efficiency support.

Public source selection and real adapter validation begin in C5.2. Synthetic Continuity augmentation begins only after the real source layer is explicit.

## C5.1 exit conditions

C5.1 is complete when:

1. the normalized schema and provenance classes are implemented;
2. malformed identity, timing, token, prefix, checksum, and provenance states reject;
3. source order and chronological replay order are independently preserved;
4. missingness/coverage/required-field behavior is deterministic;
5. canonical JSON round trip and fingerprint behavior are tested;
6. unknown/missing/non-finite/duplicate JSON structures reject;
7. synthetic Continuity fields cannot enter the source-record schema unnoticed;
8. Python 3.11/3.12/3.13 exact-head CI is green;
9. bounded exact-head review finds no unresolved schema/provenance-integrity blocker;
10. the slice is SHA-fenced and squash-merged before C5.2 source selection/adapter work begins.
