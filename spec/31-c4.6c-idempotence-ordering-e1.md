# C4.6c — Measured Distributed S5 Idempotence / Ordering EV1

Status: candidate implementation for issue #88 under C4.6/S5 #83.

Base milestone: `d42a77916bea57d24c158e7aa1c9e525f85e408a` (C4.6b closure).

## Purpose

This final S5 slice evaluates duplicate/reordered semantic delivery at a real CPU-process/IPC boundary. It does not change C1/C2/C3. The measured question is whether physical duplicate or late observations can create a second authoritative completion or restore older semantic authority.

Validation class: `EV1_MEASURED_CPU_DISTRIBUTED`.
Result provenance: `MEASURED`.

## Physical measurement boundary

Three independent `spawn` worker processes (`w1`, `w2`, `w3`) communicate with the coordinator over `multiprocessing.Pipe`. Workers execute bounded CPU work and emit observation messages; only the coordinator owns and mutates ContinuityCore semantic state.

Every physical delivery records:

```text
physical_delivery_id
semantic_event_id
action
worker_id
worker_pid
semantic_observed_at
started_at
completed_at
delivered_at
process_cpu_seconds
wall_execution_seconds
cpu_digest
coordinator_sequence
```

The worker caches semantic identity: repeated emission of the same semantic EventID preserves its first semantic-observation timestamp and semantic action while producing a distinct physical delivery measurement. This models duplicate delivery of one semantic observation rather than silently assigning a new semantic identity to every transport arrival.

Every physical delivery satisfies a non-zero process-CPU floor. Worker PID/identity and response kinds are checked by the coordinator.

## Measurement-before-policy replay

For paired evaluation, every scenario is physically measured exactly once. The resulting immutable ordered delivery tuple and worker PID set are replayed unchanged against fresh semantic runtimes for B0-B4. Policy choice therefore cannot influence process scheduling, timestamps, CPU durations, or delivery order.

## Frozen scenario corpus

Issue #88 predeclared the complete corpus before implementation.

### A — duplicate final result

w1 emits semantic result `S5:EV1:A:result` twice through distinct physical delivery IDs. The first delivery creates measured exact Evidence/output o1 and finalizes r1. The duplicate delivery reconstructs the identical semantic Evidence identity and replays finalization.

Independent target:

```text
r1 COMPLETED
committed_attempt_id = a1
authoritative_output_id = o1
a1 = COMMITTED
one independently observed finalization effect
```

Faulted; actual completed request creates one policy-derived DFR opportunity.

### B — conflicting late result

w1 emits o1, then w2 emits a distinct o2 result for the same successful Attempt. Measured Evidence/output objects are created from their worker deliveries before semantic application.

Independent target: completed r1 remains immutable at a1/o1; late o2 cannot replace authority. One actual completion creates one DFR opportunity.

### C — reordered old A1 after A2

Semantic setup starts and succeeds A1, then starts A2 (superseding A1) and succeeds A2 before physical deliveries are replayed. w2's measured A2/o2 result arrives first; w1's old A1/o1 result arrives later.

Independent target:

```text
r1 COMPLETED
committed_attempt_id = a2
authoritative_output_id = o2
a1 = SUPERSEDED
a2 = COMMITTED
```

The old delivery may explicitly reject but cannot regain authority. One actual completion creates one DFR opportunity.

### D — duplicate EventID

w1 emits primary semantic EventID `S5:EV1:D:event-1`, w3 emits unrelated `S5:EV1:D:event-u`, and w1 emits the primary EventID again.

Independent normalized target: exactly one primary semantic Event and one unrelated semantic Event, with their original identity/payload. No request completion occurs, so DFR denominator remains null.

### E — single-result positive control

w1 emits one valid terminal result. Normal first finalization must remain functional. This is nonfaulted and therefore carries no Gate opportunity.

## Measured Evidence construction

For request-result actions, ExactObservation Evidence is constructed from the measured worker semantic observation:

```text
EvidenceID = evidence:<semantic_event_id>
source     = worker identity + semantic EventID
authority  = EXACT_OBSERVATION
status     = VALID
observed_at = worker semantic_observed_at
scope      = current Attempt
claim_key  = attempt:<id>:terminal-outcome
claim_value = SUCCEEDED
```

Duplicate physical delivery of the same semantic EventID therefore records the same Evidence object idempotently. Delivery-specific CPU/timestamp provenance remains separately preserved in `physical_deliveries`.

## Independent finalization accounting and DFR

The coordinator counts finalization effects from authoritative Request state transitions before/after each semantic application. It does not define DFR from `finalize_request`'s return value.

DFR remains `POLICY_DERIVED`. A faulted operation receives a DFR opportunity only when replay actually reaches a completed LogicalRequest with committed Attempt and authoritative output. Under the conforming corpus, A/B/C contribute three opportunities; D retains a null denominator; E is nonfaulted and carries no Gate opportunity.

The private anti-false-zero path first executes the real measured duplicate schedule for A safely, then injects a second authoritative-output transition. It must create both a normalized snapshot mismatch and duplicate-finalization violation and classify O4.

## Baseline fairness

Every B0-B4 policy receives the same measured physical schedules and common semantic replay. No baseline loses ordinary C1 request immutability, Attempt fencing, EventID deduplication, or Evidence requirements. No policy-specific S5 information surface is added.

A semantic null comparator is acceptable and expected if the common semantic mechanism is sufficient.
