# 1. Research boundary

C4.3a evaluates deterministic State-lineage safety without changing C1, C2, C3, or the C4.1 correctness contract.

RQ2 asks whether causal State lineage prevents reuse of physically attractive but logically incompatible State.

Primary correctness metrics in this slice are:

```text
WBRR
WSCR
SSER
```

The closed C3 baseline information contracts remain unchanged:

```text
B0  request/load only
B1  candidate-key cache locality
B2  session affinity + candidate locality
B3  exact StateID + precise State location, causally blind
B4  complete Continuity context + C1 state_compatible(...)
```

C3 returns `PlacementDecision`. It does not return a State-consumption decision.

---

# 2. Four distinct experiment stages

C4.3a keeps four operations separate:

```text
policy placement
    !=
worker execution rule
    !=
State consumption event
    !=
terminal execution / authoritative finalization
```

No metric or O-class is inferred by collapsing these stages.

## 2.1 Policy-neutral State-consumption directive

Every policy is followed by the same worker execution directive:

```text
CONSUME_DECLARED_CANDIDATE_IF_VALID_REPLICA_IS_LOCAL
```

The post-placement execution function:

```text
_execute_consumption_directive(runtime, decision)
```

has no `PolicyID` parameter and does not inspect `PlacementDecision.reason`.

It emits a concrete `StateConsumptionEvent` only when:

```text
selected worker exists
candidate replica exists
replica StateID matches the declared candidate
replica status == VALID
replica location == selected worker
```

The event records:

```text
event_id
directive_id
state_id
replica_id
worker_id
```

Consequences:

- worker placement alone is not consumption;
- B2 session affinity alone cannot manufacture consumption;
- a LOST replica cannot be consumed even when its old worker is selected;
- the same physical worker/replica condition produces the same consumption event independent of policy identity or placement reason;
- WBRR and WSCR are driven by the execution event, not by inferred policy intent.

## 2.2 Explicit terminal execution and finalization

A State-consumption violation is not automatically O4.

After the consumption stage, every trial executes an explicit terminal stage under the common rule:

```text
EXECUTE_PATH_AND_FINALIZE_CURRENT_ATTEMPT
```

The experiment holds an application-level expected result token outside policy-visible input.

The deterministic terminal rule is:

```text
no candidate consumption
    -> recompute
    -> expected result token

compatible candidate consumption
    -> expected result token

incompatible candidate consumption
    -> distinct wrong result token
```

The consumer Attempt is then physically completed, terminal completion Evidence is recorded, a terminal Output is created, and C1 `finalize_request(...)` is invoked.

A `TerminalExecutionEvent` records:

```text
event_id
request_id
attempt_id
output_id
expected_result_token
actual_result_token
consumed_state_id
used_recompute
reported_success
authoritative_commit
semantically_correct
terminal_rule
```

C4.3a classifies O4 only when all are observed:

```text
reported_success == true
authoritative_commit == true
actual_result_token != expected_result_token
```

Therefore a wrong-State read and a silent incorrect committed success remain distinct facts.

If a future execution path detects bad consumption and recomputes before commit, that path must classify as correct degraded recovery rather than O4.

## 2.3 Ground-truth snapshot boundary

Independent semantic ground truth is snapshotted before terminal finalization mutates the consumer request/Attempt from:

```text
current Attempt
```

to:

```text
committed Attempt
```

This preserves the pre-decision execution context used for compatibility classification and prevents terminal mutation from contaminating the oracle record.

# 3. Independent semantic oracle

Ground-truth compatibility classification does not call:

```text
ContinuityCore.is_ancestor(...)
ContinuityCore.state_compatible(...)
```

The experiment independently checks the covered C4.3a dimensions:

```text
ExecutionContext object/link consistency
consumer Attempt is CURRENT
State exists
State validity == VALID
origin Continuation exists
origin and consumer share the Session
origin Continuation is an ancestor of the consumer Continuation
producer Attempt exists when declared
producer Attempt is not SUPERSEDED
completed producer Request committed that producer Attempt
```

Phase-origin and derived-State dependency pressure are intentionally deferred to C4.3b.

For every trial, C1 `state_compatible(...)` is separately evaluated and required to agree with the independent oracle before terminal execution begins. A disagreement aborts the experiment rather than becoming policy-visible evidence.

# 4. Deterministic scenarios

Canonical order:

```text
FTR4
FTR5
FTR14
S2-SIMILAR-DIFFERENT
S2-VALID-ANCESTOR
FTR6
```

## 4.1 FTR4 — wrong sibling State

```text
C0
├── C1 -> X-sibling @ w1
└── C2 -> consumer
```

The candidate is physically valid and content-plausible but not ancestor-compatible with C2.

This is a WBRR opportunity and becomes a WSCR opportunity only if an actual consumption event occurs.

## 4.2 FTR5 — superseded-producer State

Canonical fault:

```text
C1 / Rp
├── A1 -> X1 @ w1
└── A2 commits

A1 = SUPERSEDED
```

`X1` is created while A1 is CURRENT and remains physically VALID after A2 supersedes and commits. A later descendant request is then evaluated.

Expected semantic rule:

```text
X1 rejected for later cross-request reuse
```

FTR5 contributes WSCR pressure when consumed but not WBRR because the incompatibility is producer Attempt authority rather than sibling/unrelated branch ancestry.

## 4.3 FTR14 — abandoned-branch residual State

State produced under C1 remains physically VALID after C1 becomes `ABANDONED`; sibling C2 becomes active.

Physical persistence must not restore abandoned causal authority.

## 4.4 S2-SIMILAR-DIFFERENT

```text
X-compatible      origin C0   @ w2
X-similar-wrong  origin C1   @ w1
consumer          sibling C2
```

Both States are `PREFIX/KV`; causal lineage is the discriminating fact.

## 4.5 S2-VALID-ANCESTOR control

```text
C0 -> X-ancestor @ w1
 |
 +-> C2 consumer
```

This is non-faulted. B4 must still consume compatible State when the runtime presents a valid local candidate. Safety may not be achieved by disabling reuse globally.

This control carries no Gate G1 opportunity and does not enter faulted SSER denominators.

## 4.6 FTR6 — lost valid State

A logically compatible ancestor State exists but its only physical replica is `LOST`.

Expected behavior:

```text
recompute / repair / fail
not consume the lost replica
```

The physical replica remains in independent ground truth with status `LOST`; the policy-visible location tuple is empty.

# 5. Baseline fairness boundary

Every incompatible comparator candidate is:

```text
real C1 State identity
StateValidity.VALID
PREFIX / KV representation
physically resident as a VALID replica on w1
candidate-key plausible
```

B3 receives the exact candidate StateID and precise location exactly as its closed C3 contract permits.

No C1 ancestry, producer-authority result, or application expected-result token is exposed to B0-B3.

Worker layout is:

```text
w1  candidate-local, normalized load 1
w2  non-local, normalized load 0
```

Thus:

- B0 naturally prefers w2 by load;
- B1 can prefer w1 by candidate locality;
- B2 can prefer w1 by locality/session affinity;
- B3 can prefer w1 by exact-State locality;
- B4 prefers w1 only after its declared compatibility guard succeeds; otherwise it falls back to load.

The same worker execution directive and terminal execution rule are applied after placement for every baseline.

# 6. Metric and outcome causality

## 6.1 WBRR

Exogenous paired WBRR opportunities exist for exactly:

```text
FTR4
FTR14
S2-SIMILAR-DIFFERENT
```

Every policy receives the same opportunity EventID for a scenario.

A WBRR violation requires an explicit `StateConsumptionEvent` consuming the incompatible branch candidate.

## 6.2 WSCR

WSCR is policy-derived.

A denominator exists only when the runtime emits a real State-consumption event during a faulted operation.

An incompatible consumed State increments the numerator.

A policy that recomputes without consumption has no fabricated WSCR denominator.

## 6.3 SSER / O-class

SSER is not derived from WSCR or WBRR.

The terminal event independently determines semantic outcome:

```text
incompatible State consumed
+ wrong terminal token
+ C1 authoritative finalization
    -> O4

incompatible State avoided
+ recomputation
+ correct C1 authoritative finalization
    -> O2

lost State not consumed
+ recomputation
+ correct C1 authoritative finalization
    -> O2

compatible State consumed
+ correct terminal token
+ authoritative finalization
    -> O1 when non-faulted
```

# 9. Evidence discipline

Every reported C4.3a trial uses:

```text
validation level      EV0_DETERMINISTIC_SEMANTICS
evidence provenance   SYNTHETICALLY_GENERATED
```

`ground_truth` contains policy-independent scenario facts, physical replica truth, the common consumption directive, pre-finalization independent compatibility, terminal execution rule, and expected application result token.

`policy_decision` contains only the closed C3 placement result plus declarations of which semantic guard is policy-visible. It contains no inferred consumption action and no expected result token.

`observed_evidence` contains selected worker, actual replica status, the C1 compatibility cross-check, explicit State-consumption event if emitted, and explicit terminal execution/finalization event.

The independent compatibility oracle and application result oracle remain unavailable to policy logic.
