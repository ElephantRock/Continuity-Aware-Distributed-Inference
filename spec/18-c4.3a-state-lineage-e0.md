# 1. Research boundary

C4.3a evaluates deterministic State-lineage safety without changing C1, C2, C3, or the C4.1 correctness contract.

RQ2 asks whether causal State lineage prevents reuse of physically attractive but logically incompatible State.

Primary correctness metrics in this slice are:

```text
WBRR
WSCR
SSER
```

The closed C3 baseline information contracts remain unchanged:

```text
B0  request/load only
B1  candidate-key cache locality
B2  session affinity + candidate locality
B3  exact StateID + precise State location, causally blind
B4  complete Continuity context + C1 state_compatible(...)
```

C3 returns `PlacementDecision`. It does not return a State-consumption decision or an application result.

# 2. Five distinct experiment stages

C4.3a keeps five operations separate:

```text
policy placement
    !=
worker execution rule
    !=
State consumption event
    !=
application result production / detection / recovery
    !=
authoritative terminal finalization
```

No Gate metric or O-class is inferred by collapsing these stages.

## 2.1 Policy-neutral State-consumption directive

Every policy is followed by the same worker execution directive:

```text
CONSUME_DECLARED_CANDIDATE_IF_VALID_REPLICA_IS_LOCAL
```

The post-placement execution function:

```text
_execute_consumption_directive(runtime, decision)
```

has no `PolicyID` parameter and does not inspect `PlacementDecision.reason`.

It emits a concrete `StateConsumptionEvent` only when:

```text
selected worker exists
candidate replica exists
replica StateID matches the declared candidate
replica status == VALID
replica location == selected worker
```

The event records:

```text
event_id
directive_id
state_id
replica_id
worker_id
```

Consequences:

- worker placement alone is not consumption;
- B2 session affinity alone cannot manufacture consumption;
- a LOST replica cannot be consumed even when its old worker is selected;
- the same physical worker/replica condition produces the same consumption event independent of policy identity or placement reason;
- WBRR and WSCR are driven by the execution event, not by inferred policy intent.

## 2.2 Policy-hidden application execution profile

State compatibility and terminal application semantics are intentionally independent causal inputs.

Each scenario predeclares a policy-hidden `ApplicationExecutionProfile` with one of three effects:

```text
CORRECT_RESULT
WRONG_UNDETECTED
DETECT_AND_RECOMPUTE
```

The profile is part of paired ground truth and is identical across B0-B4 for a scenario. It is not passed into any C3 policy view or decision.

The deterministic EV0 corpus intentionally includes incompatible consumed States with all three effects:

```text
FTR4                    WRONG_UNDETECTED
FTR5                    DETECT_AND_RECOMPUTE
FTR14                   WRONG_UNDETECTED
S2-SIMILAR-DIFFERENT    CORRECT_RESULT
```

Thus the predicate that defines an incompatible State consumption cannot determine O-class or SSER.

The valid-ancestor control uses `CORRECT_RESULT`. FTR6 also declares `CORRECT_RESULT`, but its LOST replica is never consumed and execution recomputes instead.

## 2.3 Result-bearing terminal execution and C1 finalization

After consumption, every trial executes the common rule:

```text
EXECUTE_APPLICATION_PROFILE_AND_FINALIZE_CURRENT_ATTEMPT
```

The expected application result token remains outside policy-visible input.

Application execution is defined without a compatibility argument:

```text
no candidate consumption
    -> recompute
    -> expected result

candidate consumed + CORRECT_RESULT
    -> candidate result == expected result
    -> no recompute

candidate consumed + WRONG_UNDETECTED
    -> candidate produces distinct wrong result
    -> no detection or recompute

candidate consumed + DETECT_AND_RECOMPUTE
    -> candidate produces a detected bad result
    -> recompute before terminal commit
    -> expected result
```

The current consumer Attempt is then completed. The actual application result token is recorded in `EXACT_OBSERVATION` Evidence whose scope contains both:

```text
("attempt", AttemptID)
("result_token", actual_result_token)
```

The terminal C1 `Output` references that Evidence. C1 `finalize_request(...)` then establishes authority for the result-bearing Output.

A `TerminalExecutionEvent` records at least:

```text
event_id
request_id
attempt_id
result_evidence_id
output_id
application_profile_id
application_effect
expected_result_token
candidate_result_token
actual_result_token
consumed_state_id
detected_bad_state
used_recompute
reported_success
authoritative_commit
semantically_correct
terminal_rule
```

C4.3a classifies O4 only when:

```text
reported_success == true
authoritative_commit == true
actual_result_token != expected_result_token
```

A WSCR/WBRR violation therefore may coexist with O1, O2, or O4 depending on independently declared application execution.

## 2.4 Ground-truth snapshot boundary

Independent semantic ground truth is snapshotted before terminal finalization mutates the consumer request/Attempt from CURRENT to COMMITTED.

This preserves the pre-decision execution context used for compatibility classification and prevents terminal mutation from contaminating the oracle record.

# 3. Independent semantic oracle

Ground-truth compatibility classification does not call:

```text
ContinuityCore.is_ancestor(...)
ContinuityCore.state_compatible(...)
```

The experiment independently checks the covered C4.3a dimensions:

```text
ExecutionContext object/link consistency
consumer Attempt is CURRENT
State exists
State validity == VALID
origin Continuation exists
origin and consumer share the Session
origin Continuation is an ancestor of the consumer Continuation
producer Attempt exists when declared
producer Attempt is not SUPERSEDED
completed producer Request committed that producer Attempt
```

Phase-origin and derived-State dependency pressure are intentionally deferred to C4.3b.

For every trial, C1 `state_compatible(...)` is separately evaluated and required to agree with the independent compatibility oracle before application execution. A disagreement aborts the experiment rather than becoming policy-visible evidence.

Application-result production is separately determined by the predeclared application profile and does not consume the compatibility result.

# 4. Deterministic scenarios

Canonical order:

```text
FTR4
FTR5
FTR14
S2-SIMILAR-DIFFERENT
S2-VALID-ANCESTOR
FTR6
```

## 4.1 FTR4 — wrong sibling State

```text
C0
├── C1 -> X-sibling @ w1
└── C2 -> consumer
```

The candidate is physically valid and content-plausible but not ancestor-compatible with C2. This is a WBRR opportunity and becomes a WSCR opportunity only if an actual consumption event occurs.

Application effect: `WRONG_UNDETECTED`.

## 4.2 FTR5 — superseded-producer State

Canonical fault:

```text
C1 / Rp
├── A1 -> X1 @ w1
└── A2 commits

A1 = SUPERSEDED
```

`X1` is created while A1 is CURRENT and remains physically VALID after A2 supersedes and commits. A later descendant request is then evaluated.

Expected State-safety rule:

```text
X1 rejected for later cross-request reuse
```

FTR5 contributes WSCR pressure when consumed but not WBRR because the incompatibility is producer Attempt authority rather than sibling/unrelated branch ancestry.

Application effect: `DETECT_AND_RECOMPUTE`. If a weaker baseline consumes X1, WSCR is still violated, but the application detects the bad candidate and recovers to O2 before commit.

## 4.3 FTR14 — abandoned-branch residual State

State produced under C1 remains physically VALID after C1 becomes `ABANDONED`; sibling C2 becomes active. Physical persistence must not restore abandoned causal authority.

Application effect: `WRONG_UNDETECTED`.

## 4.4 S2-SIMILAR-DIFFERENT

```text
X-compatible      origin C0   @ w2
X-similar-wrong  origin C1   @ w1
consumer          sibling C2
```

Both States are `PREFIX/KV`; causal lineage is the discriminating State-safety fact.

Application effect: `CORRECT_RESULT`. This deliberately proves that a WBRR+WSCR violation does not mechanically imply semantic error: the incompatible candidate happens to produce the expected application result in this EV0 operation.

## 4.5 S2-VALID-ANCESTOR control

```text
C0 -> X-ancestor @ w1
 |
 +-> C2 consumer
```

This is non-faulted. B4 must still consume compatible State when the runtime presents a valid local candidate. Safety may not be achieved by disabling reuse globally.

Application effect: `CORRECT_RESULT`.

This control carries no Gate G1 opportunity and does not enter faulted SSER denominators.

## 4.6 FTR6 — lost valid State

A logically compatible ancestor State exists but its only physical replica is `LOST`.

Expected behavior:

```text
recompute / repair / fail
not consume the lost replica
```

The physical replica remains in independent ground truth with status `LOST`; the policy-visible location tuple is empty.

# 5. Baseline fairness boundary

Every incompatible comparator candidate is:

```text
real C1 State identity
StateValidity.VALID
PREFIX / KV representation
physically resident as a VALID replica on w1
candidate-key plausible
```

B3 receives the exact candidate StateID and precise location exactly as its closed C3 contract permits.

No C1 ancestry result, producer-authority result, application profile, or expected application result token is exposed to B0-B3.

Worker layout is:

```text
w1  candidate-local, normalized load 1
w2  non-local, normalized load 0
```

Thus:

- B0 naturally prefers w2 by load;
- B1 can prefer w1 by candidate locality;
- B2 can prefer w1 by locality/session affinity;
- B3 can prefer w1 by exact-State locality;
- B4 prefers w1 only after its declared compatibility guard succeeds; otherwise it falls back to load.

The same consumption directive, application profile, and terminal-finalization machinery are applied after placement for every baseline.

# 6. Metric and outcome causality

## 6.1 WBRR

Exogenous paired WBRR opportunities exist for exactly:

```text
FTR4
FTR14
S2-SIMILAR-DIFFERENT
```

Every policy receives the same opportunity EventID for a scenario.

A WBRR violation requires an explicit `StateConsumptionEvent` consuming the incompatible branch candidate.

## 6.2 WSCR

WSCR is policy-derived.

A denominator exists only when the runtime emits a real State-consumption event during a faulted operation. An incompatible consumed State increments the numerator.

A policy that recomputes without consumption has no fabricated WSCR denominator.

## 6.3 SSER / O-class

SSER is not derived from WSCR or WBRR.

The covered faulted outcomes demonstrate all required separations:

```text
FTR4 / FTR14 under B1-B3
    incompatible consumption
    + WRONG_UNDETECTED
    + wrong result-bearing Output finalized by C1
    -> O4

FTR5 under B1-B3
    incompatible consumption / WSCR violation
    + DETECT_AND_RECOMPUTE
    + correct result-bearing Output finalized by C1
    -> O2

S2-SIMILAR-DIFFERENT under B1-B3
    WBRR + WSCR violation
    + CORRECT_RESULT
    + no recompute
    + correct result-bearing Output finalized by C1
    -> O1

incompatible candidate avoided
    + recomputation
    + correct result-bearing Output finalized by C1
    -> O2
```

Gate violations and O4 are therefore empirically distinct within this deterministic corpus.

# 9. Evidence discipline

Every reported C4.3a trial uses:

```text
validation level      EV0_DETERMINISTIC_SEMANTICS
evidence provenance   SYNTHETICALLY_GENERATED
```

`ground_truth` contains policy-independent scenario facts, physical replica truth, the common consumption directive, pre-finalization independent compatibility, application execution profile, terminal execution rule, and expected application result token.

`policy_decision` contains only the closed C3 placement result plus declarations of which semantic guard is policy-visible. It contains no inferred consumption action, no application profile, and no expected result token.

`observed_evidence` contains selected worker, actual replica status, the C1 compatibility cross-check, explicit State-consumption event if emitted, and the result-bearing terminal execution/finalization event.

The independent compatibility oracle and application execution profile remain unavailable to policy logic.
